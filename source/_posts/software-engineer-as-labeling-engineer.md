最近读到 Proton CTO 的 AI 宣言《AI @ Proton, Engineering Manifesto》。里面有一句话很直接：工程师的工作，已经变成帮助 LLM 更快地写出更好的代码。宣言把工程师比作 team leader，模型和 Agent 则是下属。

我想到的是另一个职位：labeling engineer。**Software engineer 最终的出路，是标注工程师。在 LLM 无法自行获得 ground truth 的地方，人负责提供判断。** 这个名字没有「管理 AI 团队」那么体面，但更接近人实际在做的事。

## 你每天都在给模型打标签

让 Agent 写一个功能，第一版出来，你说「不对，这种情况应该报错」；第二版出来，你说「行为对了，但不能引入这个依赖」；第三版终于过了，你点 Accept。

这几个动作，都在标注。你给出了负样本、补充了约束，最后确认了一个可接受的结果。过去，这些判断藏在你亲手写的代码里；现在，代码由模型生成，你把判断单独交了出来。

需求澄清也是如此。用户说「支持离线导出」，你知道这里的离线意味着断网后仍然能打开，意味着引用的资源要随包带走，意味着导出文件不能依赖开发者电脑上的绝对路径。把这些隐含条件说清楚，就是把一个模糊意图标成一组可检查的行为。

这也解释了为什么会写代码的人，未必能把 Agent 用好。过去可以一边实现一边修正理解，很多判断不用离开自己的脑子。现在你要让另一个执行者拿到足够明确的信号。只说「这个实现不够好」，模型收到的仍然是一句没有答案的评价。

这里的 labeling 比训练集里的分类标签更宽：它包括预期结果、反例、验收条件，也包括附带理由的偏好。它们未必进入模型权重，却会改变下一轮 Agent 能看到什么、什么结果会被放行。

## 测试通过以后谁来给答案

假设让 Agent 实现一个资料导出功能。它生成 ZIP，写了测试，验证文件存在、解压成功、目录结构正确。所有检查都绿了。

你把这个 ZIP 拿到另一台断网的电脑上，打开首页，图片全没了。Agent 把本机图片路径写进了 HTML。它的测试在原来的电脑上跑，自然发现不了问题。

再让它补一个「图片存在」的测试也没用。如果测试仍然去检查本机文件，错误理解只会多一份可执行副本。我在{% post_link agent-tdd-is-self-verification '《Agent 真的需要 TDD 吗？》' %}里讨论过这个问题：**测试最重要的不是先写，而是答案从哪里来。**

在这个例子里，答案来自使用场景：接收者只有导出包，没有原机器，也没有网络。工程师要把这个条件带进验证环境，让检查在一个无法访问原目录、无法访问网络的隔离环境里运行，并确认页面所需资源仍然能加载。

一旦这个检查建立起来，「导出包是否自包含」就不必每次靠人判断。模型可以运行工具、读取失败结果、修复引用，直到通过。人提供的那次 label，已经变成了机器可以反复执行的规则。

可功能还有下一层问题。导出时遇到缺失图片，应该阻止整个导出，还是允许用户带着提示继续？做证据归档和做个人剪贴簿，可能需要不同答案。编译器不会替你决定，ZIP 格式也没有这个规定。你得找到使用者，弄清楚漏一张图和无法导出哪个代价更大。

**能自动验证的部分交给工具；尚未确定什么才算对的部分，才是人的工作。** 这条边界会移动。今天需要讨论的规则，明天写进产品契约，就可以自动检查。工程师不该守着同一道题永远批卷。

## 人的标签也可能是错的

我在{% post_link ground-truth-core-competency-of-ai-engineering '《Ground Truth：AI 时代最被低估的竞争力》' %}里写过，不能一直拿人脑当 ground truth。人工 review 跑不过生成速度。这次还要把另一层区别说清楚：人给出了答案，不代表答案就是真相。

「包里缺了一张被引用的图片」是可以检查的事实。「缺图就禁止导出」是产品选择。「用户宁可导出失败也不能接受缺图」则是需要验证的假设。把这三句话都存成一个 approved label，下一轮 Agent 就可能把假设当成不可违背的事实。

资深工程师也会标错。他熟悉的客户可能已经不再是主要用户，他坚持的依赖边界可能服务于一个早就结束的迁移计划。他的判断有来历，也有保质期。把它写进 AGENTS.md，并不会自动延长保质期。

所以有用的标注，除了结论，还要留下证据和适用条件：哪个用户场景要求这样做，哪个事故暴露过这个问题，当前为什么接受这个代价。两个工程师意见相反时，也不该急着把其中一个标成正确答案。先看他们是不是在替不同的用户、不同的阶段做决定。

[Anthropic 的 Agent eval 指南](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)区分了代码评分、模型评分和人工评分，并指出模型评分需要用人的判断校准。这是工具分工。人的判断本身，仍然需要真实使用和结果反馈来校验。

LLM 拿不到 ground truth，可能是没有工具权限，可能是信息还没被记录，也可能是问题本来就没有唯一答案。前两种要补访问能力和证据；最后一种要明确谁做选择、接受什么代价。不能把所有缺口都填成「找个人点一下确认」。

## 标一次还是标一辈子

同一个导出问题，可以产生两种工作方式。

第一种，每次 Agent 做完，你下载 ZIP，断网，换电脑，逐页打开检查。你很负责，也很忙。模型生成得越快，你积压的验收任务越多。最后，整个团队的产出被你的可用时间封顶。

第二种，第一次发现问题后，你留下失败样本、接收者环境和预期行为，再把它们做成回归检查。后面的同类错误由系统拦住，你只处理新出现的情况，例如导出包内的链接都正常，但读者根本找不到需要的材料。

两种方式都在 labeling，积累下来的东西却完全不同。前者积累待办，后者积累能够重复使用的判断。

这也是 labeling 后面还需要 engineer 的原因。知道哪里不对，只完成了一半。你还要能隔离出失败条件，分清症状和原因，设计一个能抓住这类错误、又不会拒绝合理实现的检查。直接比较两份 ZIP 的字节就可能太死：时间戳变化不代表导出坏了。只看文件数量又太松：文件齐全不代表链接可用。

验证机制本身也需要工程判断。模型可以帮忙实现检查，但这个检查到底能证明什么，仍然要有人追究。

Proton CTO 在宣言中要求工程师让模型下次能做得更好，还提到仓库上下文、共享 skills 和对重复失败的调查。在这个意义上，「下次更好」可以完全不涉及重新训练模型：测试多了一个独立样本，工具多了一个验证能力，Agent 的执行环境就已经不同了。

## 这个职位不会收留所有程序员

把工程师叫作 AI team leader，容易让人产生一种错觉：代码不用自己写了，每个人都能原地升职，带一支不眠不休的队伍。

但如果一个工程师建立的检查可以服务很多 Agent，同一类任务需要的人就可能更少。生成量增加，并不意味着人工审核量应该同比增加；工程化的目的，恰恰是减少重复判断。labeling engineer 不是给现有岗位换个名字就能完成的安置方案。

我在{% post_link what-engineers-are-still-for '《还要工程师干什么？》' %}里对实现型岗位的判断没有变。能把明确要求翻译成代码，正在失去过去的稀缺性。剩下的工作要求你识别没有写出来的约束，找到独立于模型的证据，并把这些判断交付给系统。

这需要懂实现。看不懂资源如何被打包，就难以发现那个「图片存在」的测试验证错了对象；不理解隔离环境，就难以让下一次验证摆脱原机器。只是实现能力的用途变了：它帮助你判断模型做得对不对，以及怎样让系统自己发现不对。

Software engineer 的归宿是 labeling engineer，我说的是这个重心迁移。在模型拿不到答案的地方，人先给出有依据的判断；判断能够被验证以后，再把它交给机器。

下一次 Agent 交来那个 ZIP，你的价值不在于又打开检查了一遍，而在于上次发现的错误，这次已经不需要你来发现。

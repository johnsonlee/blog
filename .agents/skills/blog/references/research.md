# 研究型文章怎样写深

深度是分析分辨率，不是篇幅。读者不仅要知道“有哪些东西”，还要能沿着一条完整链路看见：输入怎样变成输出，中间经过哪些状态，谁控制状态转换，什么条件会让系统停住，以及这个约束会造成什么后果。

不要求每篇文章机械覆盖所有层级。先找到支撑全文判断所需的最深一层，再把选中的链路从头走通。

## 先定义读者的认知变化

研究从读者当前的困惑开始，不从资料分类开始。先写清三件事：

- 读者已经看见了什么公开现象、产品、数字或结论
- 这个表象最容易让人误判什么
- 读完以后，读者应该多看见哪一层机制、边界或因果关系

顶层问题下面会自然长出后续问题。先记录这些问题，再选择一条主线；不是每个正确的问题都要塞进同一篇文章。文章标题、章节和配图都应该服务这条主线。

## 划清分析边界

在搜索资料以前先确定：

- **分析单位**：研究的是一家公司、一个项目、一套系统、一项任务，还是一单位产能
- **起点与终点**：从哪个可观察事件或交付 gate 开始，到哪个结果结束
- **状态口径**：公告、签约、在建、送电、验收、投产，或者该主题自己的状态机
- **时间与单位**：存量还是增量，功率还是能量，shipment 还是 accepted capacity，季度数字还是 run rate
- **明确不写**：哪些相邻问题会分散主线，留给后续文章

边界不清时，资料越多，越容易把不同对象、状态和单位拼成一个看似完整的故事。

## 先建立系统模型

根据主题选择必要的视图。它们先是研究笔记，不一定都要变成正文配图。

### Anatomy

对象由哪些层级和模块组成，边界在哪里，哪些东西看起来相邻却不属于同一层。Anatomy 解决“全貌是什么”，防止正文在局部主题之间跳跃。

### Flow And State

输入沿什么 physical、digital、contractual 或 financial path 变成输出；每一步改变了什么状态，需要什么证据才能越过下一道 gate。Flow 解决“它怎样工作”，state machine 解决“做到哪一步才算数”。

### Ownership And Dependency

谁负责交付每一段，哪些工作可以并行，哪些必须等待前置输入，哪个接口没有共同 owner。Dependency graph 或 Gantt 解决“为什么不能更快”，也区分设备 lead time 与整套系统 time-to-delivery。

### Capacity And Yield

名义容量怎样经过 redundancy、conversion、loss、qualification、yield 和 utilization 变成可用输出。用同一套单位做 reconciliation，解决“新闻里的数字为什么不等于最终结果”。

### Constraint And Alternative

队列在哪里形成，failure mode 是什么，瓶颈会不会迁移；复用、扩建、替代设计或其他供应商为什么能或不能绕开约束。没有替代路径，无法判断约束是否真的刚性。

### Consequence

技术或交付约束怎样改变时间、成本、价格、竞争格局或用户体验。Investing 类文章再沿 [investing.md](investing.md) 追到订单、毛利、现金流、price-in 与证伪条件。

## 建立证据链

Claim-to-source ledger 至少记录：claim、证据、来源、时间、口径或状态、确定性，以及是否需要图来解释关系。

- 公司公告适合证明公司说了什么，不自动证明项目已经交付。
- 标准和 reference design 适合证明系统边界与要求，不自动证明某个现场照此建成。
- 第三方估算可以填补空白，但必须与公司披露和作者推论分开。
- 一条来源只支撑它真正覆盖的 claim；图表也不能替代出处。

关键数字至少要回答规模、变化、比较、约束或后果中的一个。能做 reconciliation、数量级估算或 sensitivity 时就做；无法可靠量化时明确边界，不制造精确感。

## 沿深度阶梯继续追问

研究通常从上到下穿过五层：

1. **Visible claim**：新闻、产品、合同或一个大数字说了什么
2. **Operating system**：组件和流程怎样共同工作
3. **Delivery system**：状态、owner、依赖、测试和时间怎样把系统交出来
4. **Constraint**：容量、yield、failure、替代与迁移在哪里改变结果
5. **Consequence**：约束怎样传导到业务、用户或 economics

只复述第一层是摘要；列出第二层的组件仍可能只是科普。文章需要走到哪一层，由最终判断决定，但必须至少比公开叙事多揭开一层，并把选中的链路走完。

例如，“PPA、study、agreement、energization 是四个阶段”只描述流程。继续解释为什么附近有发电厂仍送不出 1GW、customer、utility 与 regional transmission 三套 schedule 如何咬合、哪些 gate 不能并行、承诺怎样改变风险承担，读者才真正看见交付系统。这个例子说明研究分辨率，不是所有文章都要套用电网结构。

## 把模型变成问题链

大纲不是把 Anatomy、Flow、Dependency 逐项抄成章节。按读者的理解顺序重新组织：

1. 当前表象为什么让人困惑
2. 要回答它，必须先补上哪一层系统结构
3. 结构补齐以后，又出现哪个更深的约束
4. 哪组事实或数字能检验这个约束
5. 约束成立后，原来的判断需要怎样改变

只读相邻章节的结尾和开头，应当能看出为什么必须继续。章节换序后仍然成立，通常说明文章是一组知识卡片，不是一条论证链。

## 动笔前的深度检查

- 从起点到终点是否还存在用“然后”“完成后”跳过的关键转换
- 关键状态、单位、责任边界和证据是否能一一对应
- 文章是否解释了至少一个读者原本看不见的机制或约束
- 是否有足够的数字说明规模、时间或敏感变量，而不是只堆形容词
- 复用、扩建或替代路径是否会推翻“瓶颈”判断
- 结论是否由前面的模型与证据推导出来，而不是换一种说法重复新闻
- 删除任一章节是否会破坏后续推理；不会时，考虑删除或重排

配图数量、Sources 数量和篇幅都不能单独证明深度。真正的验收标准是：读者现在能不能自己沿着同一条链解释这个对象为什么会得到当前结果。

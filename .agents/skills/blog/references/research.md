# 研究型文章怎样写深

深度是读者获得的分析分辨率：原本只能看见结果，读完以后能看见决定结果的关系，并能用这些关系判断一个新案例。篇幅、Sources 数量、专业名词和图数都不能证明深度。

研究可以在后台展开成完整系统模型；正文只保留关闭“小白模型与专家模型之差”所需的部分。不要把研究完整误写成文章面面俱到。

## 锁定分析对象

搜索以前先记录：

- 对象：公司、项目、系统、任务或一单位产能
- 边界：从哪个可观察起点到哪个结果
- 状态：公告、签约、在建、送电、验收、投产，或主题自己的状态机
- 口径：存量或增量、功率或能量、shipment 或 accepted capacity、季度或 run rate
- 时空：哪个时间点、地区、监管和市场环境
- owner：谁对当前转换负责

把这组信息视为 analysis-unit lock。引用别的项目、地域、公司或时间只能承担明确的比较或机制证据；写清可比性，使用后回到锚点。不能为了补流程、数字或公司映射，悄悄更换分析对象。

## 把认知差距变成研究任务

使用 `SKILL.md` 的认知契约，不再另列一套文章问题。把每个 gap 翻译成可验证的 research question：什么区别、关系或约束会让朴素答案失效，什么现场证据、状态文件或数量关系能够证明它。小白模型要具体到一句可被证伪的话，例如“签了 PPA 就拿到了可用电力”；专家模型则写成面对新项目时会检查的状态、依赖、数量关系和证据，而不是名词全集。

## 后台系统模型

按主题选择必要视图，不要求每篇全部建立，更不能按下面顺序写正文：

- **Anatomy**：层级、模块和边界，防止把不同维度混在一起
- **Flow / State**：输入如何变成输出，每道 gate 需要什么证据
- **Ownership / Dependency**：谁负责，什么能并行，什么必须等待，接口由谁闭合
- **Capacity / Yield**：名义量经过 redundancy、loss、qualification、yield 和 utilization 后剩多少可用输出
- **Constraint / Alternative**：队列和 failure mode 在哪里，复用、扩建、换设计或供应商能否绕开
- **Consequence**：约束怎样传到时间、成本、价格、竞争和用户结果

这些是找漏项的 scratchpad，不是“标准六章”。最终判断需要哪一层就把那条链走通；其余内容留在研究笔记。

## 找到迫使模型升级的证据

Claim-to-source ledger 记录 claim、证据、来源、日期、对象、状态、单位、确定性和可复现计算。

- 公司公告证明公司披露了什么，不自动证明项目已经交付。
- 标准和 reference design 证明边界与要求，不自动证明某个现场照此建成。
- 第三方估算用于填补空白时，与公司披露和作者推论分开。
- 一个来源只支撑它覆盖的 claim；图表不能替代出处。
- 同一数量关系尽量做 reconciliation、数量级估算或 sensitivity；无法可靠量化时停止在证据边界。

优先寻找能否定朴素答案的反例、gate、约束或数量关系。更多背景资料不会自动让文章更深。

## 从研究树剪出正文路径

Research coverage 与 reader path 是两份不同产物。完整研究树用于确认没有漏掉会推翻结论的因素；正文路径按 `SKILL.md` 的认知表，只提取让朴素答案失效、补上最小模型并验证新判断所需的证据。其余正确资料留在后台。

## 深度验收

- 从起点到结论是否还存在用“然后”“完成后”掩盖的关键转换
- 状态、单位、owner 和证据能否一一对应
- 主 case 是否贯穿推理，跨对象证据是否说明了可比性
- 是否至少有一个朴素答案被具体证据推翻，而不是作者直接纠正读者
- 读者是否得到可迁移的定位、推演或验证能力
- 结论是否由系统关系和证据推出，而非重复 headline claim
- 文章是否在闭合一个问题，而不是展示作者研究了多少分支

最后用一个正文外的新案例做内部测试：读者凭文中的模型，能否知道先确认哪个状态、数字或依赖。不能，就继续研究缺失的关系，而不是增加概念介绍。
